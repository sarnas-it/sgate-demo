# On-prem и 152-ФЗ: контур данных Security Gate

Документ описывает, какие данные покидают контур заказчика в каждом варианте
развёртывания. Это техническая позиция, а не юридическое заключение:
окончательную оценку 152-ФЗ делает заказчик.

## Что делает каждый слой

| Слой | Читает | Куда уходят данные | Можно ли без внешней сети |
|---|---|---|---|
| Deps (SCA) | lock-файлы, `go.mod`, `pom.xml`, импорты в коде | имена и версии пакетов → OSV/deps.dev/npm | да, офлайн-пакет баз (`--dataset`) |
| Deps (ревью PR, LLM) | дифф PR | фрагменты диффа → API модели | да, локальная модель или выключено |
| Guardrail | дифф PR/push | никуда, работает в раннере | да |
| Semgrep | исходный код | правила из реестра Semgrep (код не уходит при `--metrics=off`) | да, локальный набор правил |
| Trivy | файлы, образы | база уязвимостей скачивается к сканеру | да, зеркало БД |
| Дашборд | метаданные находок | внутри контура или у Sarnas | да, в on-prem |

## Варианты развёртывания

### A. SaaS (быстрый старт)

- GitHub App Deps + Guardrail в CI заказчика.
- Дашборд `deps.sarnas.ru`.
- Наружу: имена/версии пакетов для OSV/deps.dev/npm, метаданные находок,
  фрагменты диффа при включённом LLM-ревью.
- Подходит, если заказчик разрешает внешний SaaS для метаданных и готов
  выключить LLM-ревью.

### B. On-prem (рекомендуется для Альфы)

Всё в контуре заказчика:

- `depsd` + Postgres + дашборд в Docker Compose;
- Guardrail как контейнер в CI;
- Semgrep с локальным набором правил;
- Trivy с зеркалом БД;
- офлайн-пакет баз Deps, подписанный ключом Sarnas, обновляется по регламенту.

Наружу не уходит ничего, кроме обновлений баз (по расписанию, через прокси).
LLM-ревью выключено или направлено на локальную модель.

### C. Гибрид

- SCA и отчёты — в контуре (офлайн-базы).
- Guardrail/Semgrep/Trivy — в CI заказчика.
- Дашборд — в контуре; Sarnas получает только агрегированные метрики пилота
  по согласованному списку.

## Данные, которые всё же нужно защищать

Даже в on-prem есть чувствительные данные:

- **находки**: имя пакета, версия, advisory, путь к файлу;
- **исключения**: кто и почему разрешил, до какого срока;
- **логи**: время, репозиторий, результат проверки;
- **артефакты**: SARIF/JSON отчёты.

Меры:

- доступ к дашборду по SSO/ Basic auth + сетевые ограничения;
- маскирование значений в Guardrail (`GUARDRAIL_REVEAL` выключен);
- срок хранения логов и отчётов — по политике заказчика;
- аудит доступа к дашборду (в пилоте — журнал приложения, не SIEM).

## 152-ФЗ: что важно

1. **Код и ПДн не должны уходить в внешний LLM без основания.** В пилоте
   LLM-ревью выключено по умолчанию; включается только по письменному
   согласованию.
2. **OSV получает только имена/версии пакетов**, не код. Для строгого режима —
   офлайн-пакет баз.
3. **Guardrail может найти ПДн в коде.** Значения маскируются, но сам факт
   находки и путь к файлу — чувствительная информация. Доступ к отчётам
   ограничивается.
4. **Локализация.** On-prem-вариант не требует трансграничной передачи.
   SaaS-вариант требует оценки заказчика.
5. **Учётные данные.** Токены GitHub/GitLab, ключи App и пароли Basic auth
   хранятся в секретах CI/контура, не в репозитории и не в логах.

## Ограничения пилота

- Нет SSO и ролевой модели ИБ — доступ к дашборду по паролю.
- Нет интеграции с SIEM и DLP.
- Нет формального аудита действий пользователей дашборда.
- Офлайн-пакет баз требует регламента обновления; в пилоте — ручное обновление.
- Юридическая оценка 152-ФЗ — на стороне заказчика.
