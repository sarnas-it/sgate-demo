# План пилота Security Gate — 3 недели

## Цель пилота

Доказать на 1–2 реальных репозиториях, что гейт **блокирует** релиз при
критических находках, **не мешает** нормальной работе и даёт ИБ проверяемый
отчёт. Пилот не внедряет продукт на все репозитории и не заменяет процессы
ИБ.

## Границы

В пилоте:

- SCA (Deps), секреты и ПДн (Guardrail), SAST (Semgrep), контейнеры/IaC
  (Trivy);
- PR-гейт и ночной отчёт;
- политика block/warn/allowlist;
- дашборд и метрики;
- runbook и передача.

Вне пилота:

- DAST;
- нативные GitLab/Jenkins-адаптеры (только CLI, если платформа не GitHub);
- SSO, ролевая модель ИБ, интеграция с SIEM;
- полное покрытие всех репозиториев организации.

## Неделя 1 — baseline и правила

| День | Что делаем | Результат |
|---|---|---|
| 1 | доступы, установка GitHub App / CLI, выбор репозиториев | доступ есть, список репозиториев зафиксирован |
| 2 | baseline-скан, снимок уязвимостей, severity | отчёт «что нашли на старте» |
| 3 | политика: что блокирует, что предупреждает, формат исключений | подписанный владельцем политики документ |
| 4 | Guardrail в PR, разбор первых ложных срабатываний | рабочий workflow секретов |
| 5 | демо для команды, ответы на вопросы | обратная связь, список правок |

**Выход недели 1:** гейт включён в режиме «предупреждать», известен baseline и
политика.

## Неделя 2 — блокировка

| День | Что делаем | Результат |
|---|---|---|
| 6–7 | Deps check run + Guardrail как обязательные проверки | PR не мержится при CRITICAL/HIGH или секрете |
| 8 | Semgrep в единый отчёт | SAST-находки в SARIF и PR-комментарии |
| 9 | разбор ложных срабатываний, allowlist с владельцем и сроком | список исключений и правило их пересмотра |
| 10 | дневной отчёт и дашборд | ИБ получает ежедневную сводку |

**Выход недели 2:** гейт в режиме «блокировать», есть первые заблокированные
PR и разобранные исключения.

## Неделя 3 — контейнеры, регламент, передача

| День | Что делаем | Результат |
|---|---|---|
| 11 | Trivy: образы и IaC | контейнерный слой в отчёте |
| 12 | метрики пилота, сверка с baseline | отчёт «до/после» |
| 13 | runbook, регламент исключений, эскалация | документы переданы |
| 14 | обучение команды, демо для ИБ | запись демо, вопросы закрыты |
| 15 | приёмка, решение о продолжении | протокол пилота |

**Выход недели 3:** работающий гейт, отчёт с цифрами, runbook, решение
«продолжаем / меняем / останавливаем».

## Критерии успеха

Пилот считается успешным, если одновременно:

1. Гейт включён на 1–2 репозиториях и блокирует PR при CRITICAL/HIGH или
   секрете.
2. Ни один релиз за неделю 2–3 не прошёл с известной CRITICAL/HIGH
   уязвимостью без явного исключения.
3. Доля ложных срабатываний разобрана и зафиксирована; по каждому исключению
   есть владелец и срок.
4. ИБ получает ежедневный отчёт и может объяснить, что в нём.
5. Команда заказчика сама включает/выключает проверку по runbook.

## Критерии остановки

- Нет владельца политики — блокировка невозможна, пилот переходит в режим
  отчёта.
- Платформа не поддерживает check run/CI-шаг — остаётся CLI и ручной запуск;
  это меняет объём пилота.
- Ложные срабатывания выше согласованного порога и не снижаются allowlist —
  пересматриваем правила, а не «отключаем гейт».

## Риски

| Риск | Что делаем |
|---|---|
| Политика не согласована к неделе 2 | эскалация владельцу пилота, режим warn |
| Нет доступа к репозиториям | пилот на демо-репозитории, перенос на реальные позже |
| Ложные срабатывания | разбор в тот же день, allowlist с сроком |
| Секреты/код уходят наружу | on-prem-вариант, LLM выключен, только имена пакетов в OSV |
| Пилот превращается в «отчёт» | критерий успеха №1 — блокировка, а не наличие отчёта |

## Артефакты пилота

- отчёт baseline и финальный отчёт «до/после»;
- политика block/warn/allowlist;
- workflow/CI-конфигурация;
- runbook;
- список исключений с владельцами и сроками;
- протокол приёмки.
