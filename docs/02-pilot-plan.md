# План пилота Security Gate — 3 недели

## Цель пилота

Доказать на 1–2 реальных репозиториях, что гейт **останавливает пайп** при
критических уязвимостях и утечках секретов/ПДн, **не мешает** нормальной
работе и даёт ИБ проверяемый отчёт. Пилот не внедряет продукт на все
репозитории и не заменяет процессы ИБ.

## Границы

В пилоте:

- SCA (Deps) в офлайн-режиме;
- секреты и ПДн (Guardrail);
- PR-гейт и ночной отчёт;
- политика block/warn/allowlist;
- дашборд и метрики;
- runbook и передача.

Вне пилота:

- SAST/DAST (Semgrep/Trivy — отдельные слои, не заявляются);
- нативные GitLab/Jenkins-адаптеры (только CLI, если платформа не GitHub);
- SSO, ролевая модель ИБ, интеграция с SIEM/DLP;
- полное покрытие всех репозиториев организации.

## Неделя 1 — baseline и правила

| День | Что делаем | Результат |
|---|---|---|
| 1 | доступы, установка GitHub App / CLI, выбор репозиториев | доступ есть, список репозиториев зафиксирован |
| 2 | офлайн-пакет баз, baseline-скан, снимок уязвимостей | отчёт «что нашли на старте», работа без сети |
| 3 | политика: что блокирует, что предупреждает, формат исключений | подписанный владельцем политики документ |
| 4 | Guardrail в PR, разбор первых ложных срабатываний | рабочий workflow секретов/ПДн |
| 5 | демо для команды, ответы на вопросы | обратная связь, список правок |

**Выход недели 1:** оба слоя включены в режиме «предупреждать», известен
baseline и политика.

## Неделя 2 — блокировка

| День | Что делаем | Результат |
|---|---|---|
| 6–7 | Deps check run + Guardrail как обязательные проверки | PR не мержится при CRITICAL/HIGH, секрете или ПДн |
| 8 | ежедневный отчёт и дашборд | ИБ получает ежедневную сводку |
| 9 | разбор ложных срабатываний, allowlist с владельцем и сроком | список исключений и правило их пересмотра |
| 10 | проверка на реальных PR команды | первые заблокированные PR и разобранные исключения |

**Выход недели 2:** гейт в режиме «блокировать», есть доказательство остановки
пайпа на реальном коде.

## Неделя 3 — регламент и передача

| День | Что делаем | Результат |
|---|---|---|
| 11 | метрики пилота, сверка с baseline | отчёт «до/после» |
| 12 | runbook, регламент исключений, эскалация | документы переданы |
| 13 | офлайн-обновление баз, проверка восстановления | процедура обновления работает |
| 14 | обучение команды, демо для ИБ | запись демо, вопросы закрыты |
| 15 | приёмка, решение о продолжении | протокол пилота |

**Выход недели 3:** работающий гейт, отчёт с цифрами, runbook, решение
«продолжаем / меняем / останавливаем».

## Критерии успеха

Пилот считается успешным, если одновременно:

1. Гейт включён на 1–2 репозиториях и останавливает PR при CRITICAL/HIGH,
   секрете или ПДн.
2. Ни один релиз за неделю 2–3 не прошёл с известной CRITICAL/HIGH
   уязвимостью без явного исключения.
3. Доля ложных срабатываний разобрана и зафиксирована; по каждому исключению
   есть владелец и срок.
4. ИБ получает ежедневный отчёт и может объяснить, что в нём.
5. Команда заказчика сама включает/выключает проверку по runbook.
6. Сканирование работает без выхода в интернет: проверено на стенде с
   отключённой сетью.

## Критерии остановки

- Нет владельца политики — блокировка невозможна, пилот переходит в режим
  отчёта.
- Платформа не поддерживает check run/CI-шаг — остаётся CLI и ручной запуск;
  это меняет объём пилота.
- Ложные срабатывания выше согласованного порога и не снижаются allowlist —
  пересматриваем правила, а не «отключаем гейт».
- Офлайн-пакет баз нельзя обновлять по регламенту — on-prem-вариант
  пересматривается.

## Риски

| Риск | Что делаем |
|---|---|
| Политика не согласована к неделе 2 | эскалация владельцу пилота, режим warn |
| Нет доступа к репозиториям | пилот на демо-репозитории, перенос на реальные позже |
| Ложные срабатывания | разбор в тот же день, allowlist с сроком |
| Секреты/код уходят наружу | офлайн-пакет баз, LLM выключен, сеть не используется |
| Пилот превращается в «отчёт» | критерий успеха №1 — остановка пайпа, а не наличие отчёта |
| Пакет баз устарел | проверка свежести в Deps, регламент обновления и алерт |

## Артефакты пилота

- отчёт baseline и финальный отчёт «до/после»;
- политика block/warn/allowlist;
- workflow/CI-конфигурация;
- офлайн-пакет баз и регламент обновления;
- runbook;
- список исключений с владельцами и сроками;
- протокол приёмки.
