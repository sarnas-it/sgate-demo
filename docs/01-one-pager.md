# Security Gate для АльфаСтрахования — one-pager

**Кому:** АльфаСтрахование, блок разработки и ИБ.
**Что:** автоматический контроль безопасности в CI/CD — один гейт на четыре
проверки, который блокирует релиз при критических находках.
**Срок пилота:** 3 недели, 1–2 репозитория.
**Основа:** Deps (SCA) и Guardrail (секреты/ПДн) уже работают; Semgrep и Trivy
добавляются в пилоте.

## Проблема

Проверки безопасности либо не встроены в пайплайн, либо живут отдельным
отчётом, который никто не читает перед релизом. В результате критическая
уязвимость уходит в прод, а ИБ узнаёт о ней из инцидента или от аудитора.

## Решение

Композитный гейт в том же пайплайне, где живёт код:

```
PR / push ──► Guardrail   секреты и ПДн в диффе
          ──► Deps       уязвимые зависимости, OSV, достижимость
          ──► Semgrep    SAST
          ──► Trivy      контейнеры и IaC
                     │
                     ▼
        Политика: CRITICAL/HIGH — стоп, MODERATE — предупреждение
                     │
                     ├──► check run / комментарий в PR
                     ├──► issue «ежедневный отчёт»
                     └──► дашборд и история
```

Что это даёт:

- **блокировка релиза** по CRITICAL/HIGH, а не «отчёт для галочки»;
- **план исправления**: до какой версии обновить, какие breaking changes;
- **приоритизация**: достижимые уязвимости и прямые зависимости вперёд;
- **один язык** для разработки и ИБ: SARIF, check run, issue, дашборд;
- **предсказуемая стоимость**: ≈3–6 ₽ за ревью PR, дневной лимит настраивается.

## Что уже работает

- Deps: разбор 7 типов lock-файлов, OSV/deps.dev/npm, CVSS и severity,
  достижимость (`govulncheck` для Go), план обновления, GitHub App,
  комментарий в PR, check run, ночной обход, issue, дашборд.
- Guardrail: дифф PR/push, правила секретов и ПДн РФ, SARIF/JSON, allowlist,
  маскирование значений, контейнерное действие для GitHub.
- Живой пример: [issue #152](https://github.com/sarnas-it/web-sarnas/issues/152)
  — 11 уязвимостей, 4 новых, 2 CRITICAL RCE в `next 16.3.8`.

## Что добавляем в пилоте

- Semgrep (SAST) и Trivy (контейнеры/IaC) в единый отчёт.
- Политику block/warn/allowlist с владельцем и сроком исключений.
- Адаптеры GitLab/Jenkins (CLI уже есть).
- Дашборд: агрегация по репозиториям и метрики пилота.
- Runbook и передачу команде заказчика.

## Честные границы

- **SAST/DAST не заявляем готовыми.** Semgrep — слой пилота, DAST — отдельная
  оценка.
- **GitLab/Jenkins** — через CLI; нативные адаптеры — работа пилота.
- **Ложные срабатывания** неизбежны; достижимость и allowlist снижают шум, но
  калибровка идёт на репозиториях заказчика.
- **On-prem/152-ФЗ** — под требования; базовый сценарий описан в
  [`04-on-prem-152fz.md`](04-on-prem-152fz.md), юридическую оценку делает
  заказчик.

## Метрики пилота

| Метрика | Как считаем |
|---|---|
| Уязвимости по severity | снимок Deps на старте и в конце |
| Доля достижимых | отчёт Deps |
| Время до исправления | от первого срабатывания до зелёного PR |
| Заблокированные PR | журнал check run |
| Ложные срабатывания | разбор с командой заказчика, доля от всех находок |

## Что нужно от Альфы

1. 1–2 репозитория для пилота и языки/экосистемы.
2. Платформа: GitHub, GitLab или Jenkins; self-hosted или облако.
3. Что блокирует релиз: CRITICAL/HIGH, только достижимые или всё.
4. Требования к развёртыванию: SaaS-дашборд или контейнер в контуре, 152-ФЗ.
5. Владелец политики и срок пилота.
