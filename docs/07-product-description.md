# SGATE — контроль безопасности на входе в CI/CD

Документ для потенциального заказчика: что за продукт, какую задачу решает,
что уже проверено и как выглядит пилот. Технические детали — в
[`03-runbook.md`](03-runbook.md) и [`gost/`](gost/).

## Коротко

SGATE — гейт безопасности, который ставится между разработчиком и продакшеном.
На каждый pull request и push он проверяет три вещи: **уязвимые зависимости**,
**секреты и персональные данные** в диффе и **небезопасный код** (инъекции).
Нашёл блокирующую проблему — пайплайн остановлен. Не нашёл — пайплайн идёт
дальше. Всё работает внутри контура заказчика: ни код, ни имена пакетов не
уходят наружу.

## Какую задачу решает

- Уязвимая версия библиотеки или ключ в коде уходят в прод, а ИБ узнаёт об
  этом из инцидента, а не из ревью.
- Отчёт сканера приходит «после факта» и никто его не читает перед релизом.
- Внешние SaaS-сканеры нельзя: закрытый контур, 152-ФЗ, запрет на передачу
  кода и имён пакетов.
- Сканеры дают сотни предупреждений, из которых непонятно, что чинить.

SGATE отвечает на это гейтом в процессе разработки и проверяемыми метриками
качества.

## Что входит в продукт

| Слой | Что проверяет | Что блокирует | Сеть |
|---|---|---|---|
| **Deps** (SCA) | уязвимые версии пакетов по базе OSV/БДУ, достижимость для Go | CRITICAL/HIGH | не нужна: офлайн-пакет баз |
| **Guardrail** | ключи, токены, пароли, ПДн (телефон, email, ИНН, СНИЛС, паспорт) в диффе | любую находку | не нужна |
| **SAST** | инъекции команд и SQL, небезопасная работа с файлами и сетью, самопровозглашённая идентичность | ERROR | не нужна: локальные правила |

SAST — не один универсальный движок, а набор модулей с общим контрактом
(«репозиторий → SARIF + признак, что файлы действительно просканированы»):
Semgrep с локальными правилами, собственные AST-модули для Go и Python,
межпакетный taint и SSA-проход для косвенных вызовов. Языки и правила
добавляются без переделки ядра.

## Как это выглядит в работе

1. Разработчик открывает PR.
2. Гейт запускает три слоя и возвращает check run и комментарий в PR.
3. Находка блокирующего уровня останавливает merge; политика block/warn и
   allowlist с владельцем и сроком настраиваются.
4. Раз в сутки приходит отчёт по зависимостям (issue), история — в дашборде.
5. Результаты в SARIF — совместимы с GitHub Code Scanning и другими
   потребителями SARIF.

## Доказанная точность

Мы не продаём «сканер, который всё находит». Мы измеряем две величины по
ГОСТ Р 71207-2024: долю ложных срабатываний (10.4) и долю пропусков (10.5).

| Проверка | Результат |
|---|---|
| Синтетический корпус, 10 072 000 строк, 128 000 известных дефектов | найдено 128 000, пропущено 0, ложных 0 (порог 8.4 пройден) |
| Реальные проекты с CVE (pre-fix коммиты): listmonk — SQL-инъекция, OliveTin — инъекция команд | найдены оба, пропусков 0 |
| Шесть закрытых пилотов на реальных репозиториях | подтверждённые находки, задачи на исправление заведены в трекеры заказчиков |
| Демо-стенд «гейт в действии» | 7 из 7 сценариев: секрет, ПДн, CRITICAL-зависимость, исправление, чистый дифф, Go-инъекция, PHP-инъекция |

Важная оговорка: на реальном коде предупреждения требуют разбора
(триажа) — часть из них относится к коду вне атакуемой поверхности. Процедура
разбора и учёт «не триажено» отдельно от «ложно» — ближайшая задача
продукта. Мы показываем это честно, а не прячем за словом «0 находок».

## Варианты развёртывания и 152-ФЗ

- **SaaS** — быстрый старт: GitHub App, дашборд, внешняя база OSV. Подходит,
  если организация допускает внешний сервис для метаданных.
- **On-prem** — рекомендуется для корпоративного контура: все компоненты,
  офлайн-пакет баз и правила внутри периметра; наружу не уходит ничего.
- Техническая позиция по данным и 152-ФЗ — [`04-on-prem-152fz.md`](04-on-prem-152fz.md).
  Юридическое заключение даёт организация; мы предоставляем описание потоков
  данных.

## Пилот за 3 недели

| Неделя | Что делаем | Результат |
|---|---|---|
| 1 | установка на 1–2 репозитория, офлайн-пакет баз, политика в режиме warn | гейт работает, есть первые находки |
| 2 | режим block, разбор ложных срабатываний, allowlist с владельцем и сроком | доказательство остановки пайпа на реальном коде |
| 3 | метрики «до/после», runbook, передача команде | регламент и отчёт пилота |

Метрики пилота: уязвимости по severity, доля достижимых, время до
исправления, заблокированные PR, найденные секреты и ПДн, доля ложных
срабатываний после разбора.

## Ограничения (честно)

- **DAST** сейчас пассивный (аудит по OWASP WSTG); активные проверки — в
  разработке и только на согласованных стендах.
- **GitLab и Jenkins** подключаются через CLI; нативные адаптеры — после
  пилота.
- **SAST** сейчас Go и PHP; новые языки — отдельные модули по тому же
  контракту.
- **Ложные срабатывания неизбежны**; их снижают достижимость, allowlist и
  триаж, а не обещания «всё точно».
- **Порог 8.4 на реальном коде** требует разбора предупреждений — это
  ближайшая задача (SGATE-56).

## Дорожная карта

1. Триаж и снижение ложных срабатываний на реальном коде (SGATE-56).
2. Генератор отчёта (PDF/HTML) из прогона SGATE — без ручной вёрстки.
3. On-prem-пакет: установка одной командой + smoke-проверка.
4. Адаптеры GitLab/Jenkins, дашборд SAST.
5. DAST: активные проверки на авторизованных стендах.
